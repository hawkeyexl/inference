## The catalog

```ts
const LLAMA_MODELS: Readonly<Record<string, LlamaModelEntry>>;

interface LlamaModelEntry {
  uri: string;        // an exact blob path, never a :QUANT tag
  sizeBytes: number;
  license: string;
  tier?: LlamaTier;   // absent for entries outside the tier ladder
  notes: string;
}
```

| Alias | Size | Tier | License |
|---|---:|---|---|
| `granite-4.1-3b-q2` | 1.41 GB | `fast` | Apache-2.0 |
| `qwen3.5-4b` | 2.91 GB | `balanced` | Apache-2.0 |
| `qwen3.5-9b` | 5.97 GB | `quality` | Apache-2.0 |
| `gemma-4-e2b` | 2.62 GB | — | Apache-2.0 |
| `gemma-4-e4b` | 4.22 GB | — | Apache-2.0 |
| `gemma-4-12b` | 6.72 GB | — | Apache-2.0 |
| `gemma-4-26b-a4b` | 14.25 GB | — | Apache-2.0 |
| `gemma-4-e2b-q2` | 2.19 GB | — | Apache-2.0 |

All entries are unsloth GGUF builds, ungated. Each is deep-frozen.

The untiered Gemma entries backed the three tiers until [ADR 01009](https://github.com/hawkeyexl/ts-inference/blob/main/adrs/01009-retier-the-local-model-catalog-by-measurement.md)
retiered the catalog on measured results. They still resolve by name, so an existing pin keeps
working; nothing selects them automatically.

`gemma-4-e2b-q2` is kept only so existing pins resolve. **Do not choose it.** It does not
reliably terminate: on a 12-page benchmark it left 6 pages unfinished at 120 seconds, with one
still running at 400 seconds.

The catalog is a **vetted default set, not a whitelist gate** — any Hugging Face GGUF reference or
local `.gguf` path also works.

## Selectors and tiers

```ts
const LLAMA_TIERS: readonly ["fast", "balanced", "quality"];
const LLAMA_SELECTORS: readonly ["auto", "fast", "balanced", "quality"];
type LlamaTier = (typeof LLAMA_TIERS)[number];
type LlamaSelector = (typeof LLAMA_SELECTORS)[number];

function isLlamaSelector(model: string): model is LlamaSelector;
function tierForBudget(budgetBytes: number): LlamaTier;
function aliasForTier(tier: LlamaTier): string;
function uriForTier(tier: LlamaTier): string;
function resolveLlamaModelRef(model: string): string;
```

`tierForBudget` requires `sizeBytes * 3.5 <= budget`, walks tiers smallest to largest, and floors at
`fast`.

`resolveLlamaModelRef` expands an alias to its pinned URI and passes through `hf:`,
`huggingface:`, `hf.co/`, `http(s)://`, and anything ending `.gguf`. It **throws** for a selector,
and rejects a bare `user/repo` as a mistyped alias rather than guessing.

## Model files on disk

```ts
function defaultLlamaModelsDirectory(): string;
function blobNameFor(model: string): string;
function isModelDownloaded(model: string, directory: string): boolean;
function clearLlamaModels(options?: ClearLlamaModelsOptions): Promise<ClearLlamaModelsResult>;
function disposeLlamaModels(): Promise<void>;

interface ClearLlamaModelsOptions {
  directory?: string;
  models?: string[];   // aliases or URIs; omit to clear everything
  dryRun?: boolean;
}

interface ClearLlamaModelsResult {
  files: { path: string; sizeBytes: number }[];
  freedBytes: number;
  directory: string;
  dryRun: boolean;
}
```

`defaultLlamaModelsDirectory()` is `INFERENCE_MODELS_DIR` or `~/.hawkeyexl-inference/models` — this
library's **own** directory, deliberately not node-llama-cpp's shared `~/.node-llama-cpp/models`.

<Aside type="tip" title="clearLlamaModels safety guarantees">
  - Only `.gguf` and `.gguf.ipull` files are ever touched.
  - Top level only; subdirectories are never walked.
  - Loaded weights are disposed first — a memory-mapped model cannot be deleted on Windows.
  - A file held open is skipped, not forced.
  - `dryRun` reports `files` and `freedBytes` and deletes nothing.

  Pointing `directory` at a shared location still cannot take out unrelated files.
</Aside>

Selective clearing matches by **suffix**, because downloads are prefixed `hf_<user>_`, and removes
every part of a split model. An unknown name is rejected rather than silently matching nothing.

`disposeLlamaModels()` frees the process-wide weight cache and stops the
[local-model workers](#the-worker-process-and-the-backend). Weights load once per process and are
shared across providers naming the same model.

## Preparing a model

Get weights onto disk, and ask where they stand, without loading them into memory.

```ts
function ensureModel(model: string, options?: LlamaModelLifecycleOptions): Promise<EnsureModelResult>;
function modelState(model: string, options?: LlamaModelLifecycleOptions): Promise<LlamaModelState>;
function fits(model: string, options?: LlamaModelLifecycleOptions): Promise<FitsResult>;

interface LlamaModelLifecycleOptions {
  modelsDirectory?: string;  // defaults to defaultLlamaModelsDirectory()
  gpu?: LlamaGpu;            // the backend the memory probe runs on
  runtime?: LlamaRuntime;    // test seam; ensureModel then skips the runtime install
  install?: RuntimeInstallOptions;  // how an absent runtime is installed
}

interface EnsureModelResult {
  state: "downloaded" | "ready";  // "downloaded": this call fetched it
  bytes: number;                  // on disk, summed over a split model's parts
}

type LlamaModelState = "ready" | "downloading" | "missing";

interface FitsResult {
  fits: boolean;
  needBytes: number;  // the model's size times 3.5
  freeBytes: number;  // the memory the provider would have for weights
}
```

All three take what the provider takes: a catalog alias, a tier keyword or `auto`, an `hf:` URI, or
a path to a `.gguf` file. The options are the `modelsDirectory`, `gpu` and `runtime` of
`LlamaCppProviderOptions`, so one object serves both.

**`ensureModel`** downloads the weights and the `node-llama-cpp` runtime, and loads neither. The
runtime comes through [the same install path](#getting-the-runtime) as the provider's and obeys
`INFERENCE_NO_AUTO_INSTALL`. It is checked before the download, so a refused install fails before
any weights move. A model already on disk returns `"ready"` without touching the network.

Callers are serialised by a lock file, `.download-<blob>.lock`, in the models directory. A second
caller waits, and returns `"ready"` when the file appears. A lock whose process has died is
reclaimed at once. The wait is capped at two hours, and a lock older than six hours is treated as
abandoned.

**`modelState`** answers without waiting, loading or downloading. `"downloading"` means a live
process holds the download lock, or a `.ipull` partial for the model was written in the last two
minutes. A dead process's lock and a partial gone quiet are `"missing"`. A `.gguf` path that
exists is always `"ready"`. `auto` reads the runtime's memory budget to choose a tier, which can
start the [local-model worker](#the-worker-process-and-the-backend).

**`fits`** compares the model's size times the headroom `tierForBudget` uses, 3.5, with the memory
the provider would have for weights: the larger of free VRAM and half of RAM. A catalog model is
sized from the catalog. Any other model is sized from its file, so it must already be downloaded.

## The runtime seam

```ts
interface LlamaRuntime {
  resolveModelFile(uri: string, directory: string): Promise<string>;
  loadModel(path: string): Promise<LlamaLoadedModel>;
  getMemoryBudgetBytes(): Promise<number>;
}

interface LlamaLoadedModel {
  createSession(systemPrompt: string, contextSize?: number): Promise<LlamaSession>;
  dispose(): Promise<void>;
  readonly trainContextSize?: number;   // the model's training context, in tokens
  countTokens?(text: string): number | Promise<number>;   // the model's own tokenizer
}

interface LlamaSession {
  prompt(text: string, options: LlamaPromptOptions): Promise<LlamaPromptResult>;
  decide?(options: LlamaDecideOptions): Promise<LlamaDecideResult>;   // for decide()
  completeShared?(options: LlamaSharedOptions): Promise<LlamaSharedResult>;   // for completeJSONShared
  dispose(): Promise<void>;
  readonly contextSize?: number;   // tokens of context actually created
}

interface LlamaDecideOptions {
  prompts: string[];      // one user turn per question
  answerPrefix: string;   // the assistant turn opens with this; the next token is the answer
  labels: string[][];     // per prompt, the labels whose next-token probability is read
}

interface LlamaDecideResult {
  weights: Record<string, number>[];   // per prompt, label -> next-token probability
  usage?: TokenUsage;
  reuse?: LlamaDecideReuse;            // absent for a single question
}

type LlamaDecideReuse = "erase" | "checkpoint" | "reevaluate";

interface LlamaSharedOptions {
  prompts: string[];                  // one whole user turn per item
  schema: Record<string, unknown>;    // each answer is generated under its grammar
  temperature: number;
  maxTokens?: number;                 // per item
}

interface LlamaSharedResult {
  outputs: ({ text: string; stopReason?: string } | { error: string })[];   // per prompt
  usage?: TokenUsage;
  reuse?: LlamaDecideReuse;           // absent for a single item
}

interface LlamaPromptOptions {
  schema: Record<string, unknown>;
  temperature: number;
  thoughtTokens: number;
  maxTokens?: number;
}

interface LlamaPromptResult {
  text: string;
  usage?: TokenUsage;
  stopReason?: string;
}

function defaultLlamaRuntime(options?: { gpu?: LlamaGpu }): LlamaRuntime;

type LlamaGpu = "auto" | "cuda" | "vulkan" | "metal" | false;
```

`defaultLlamaRuntime()` is lazy: constructing it starts no process and loads no native code. Its
first use finds `node-llama-cpp` (a missing module raises an `InferenceError` naming
`npm i node-llama-cpp`) and starts a [worker process](#the-worker-process-and-the-backend) to run
it. The built `dist/index.js` contains only a dynamic import, so consumers without the package
still typecheck.

Inject a fake through `ProviderSpec.llamaRuntime` to test the whole local path with no weights and
no GPU. See [testing your integration](/inference/keep-it-working/testing/).

`getMemoryBudgetBytes` returns `max(free VRAM, totalmem() / 2)`, falling back to `totalmem() / 2`
when the GPU probe fails.

The provider passes `createSession` the context size it computed for the prompt, and the real
runtime treats no size as 8192. The real runtime keeps one idle context per model. A session takes
it, emptied, when it holds at least the size asked for and at most twice it. Otherwise the runtime
creates exactly the size asked for, rounded up to a multiple of 256 by llama.cpp, and disposes the
idle one. `trainContextSize` and `countTokens` are optional, so a fake written without them still
satisfies the interface. Without `countTokens`, the provider uses the 8192-token default and does
not check that the prompt fits. `countTokens` may return a promise; the real runtime's does, because
its tokenizer lives in the worker. Counts asked for in the same tick reach the worker as one request.

## `LlamaCppProvider`

```ts
class LlamaCppProvider implements DecisionProvider {
  constructor(model: string, options?: LlamaCppProviderOptions);
  // The native path completeJSONShared takes; call completeJSONShared, which validates.
  completeJSONShared(req: SharedJSONRequest): Promise<SharedJSONResponse>;
}

interface LlamaCppProviderOptions {
  runtime?: LlamaRuntime;
  thoughtTokens?: number;   // default 0
  maxTokens?: number;
  contextSize?: number;     // default: sized to each prompt, 8192 tokens at least
  modelsDirectory?: string;
  gpu?: LlamaGpu;           // default: NODE_LLAMA_CPP_GPU, else "auto"
  host?: ModelHostMode;     // default "off"; see "The model host"
  keepAlive?: number;       // ms, default 600000
  session?: string;
  hostWaitMs?: number;      // ms, default: no limit
}
```

A fresh session per call — the contract is single-shot. The schema is compiled to a GBNF grammar
**and** restated in the system prompt, because the grammar hides descriptions from the model.
Truncation at `maxTokens` is reported as an error naming the limit rather than a validation failure.

### Context size

Each call gets an empty context, sized once the prompt is known. The context is most of what a call
costs in memory beyond the weights, so this is the number that decides whether a run fits a machine.

The provider counts the tokens the call needs with the model's own tokenizer:

| Part | Tokens |
|---|---|
| System prompt, with the schema restated | counted |
| User prompt | counted |
| Chat-template overhead | 512 |
| Response | `maxTokens`, or 2048 when unset, plus `thoughtTokens` |

| `contextSize` | Context created | When the call does not fit |
|---|---|---|
| unset (default) | 8192 tokens, or the count when it is larger, up to the model's training context | error naming the training context |
| a number | exactly that many tokens | error naming `llamaCpp.contextSize` |

The context a call runs in is the last call's, emptied, when that one holds at least the size in
the table and at most twice it. So a call never gets less context than the table gives, and an idle
model holds at most one context.

A call that does not fit is never sent, because llama.cpp would shift the start of the prompt out of
the context. It fails with an `InferenceError`, which `completeValidatedJSON` and `judge` record on
`run.error`. The messages are in the [error reference](/inference/reference/errors/).

Earlier releases let node-llama-cpp choose the size, and it chose the largest context free
memory allowed. For `granite-4.1-3b-q2`, trained on 131072 tokens, a one-field prompt of about 4000
tokens took 12.9 GB on CPU. With the 8192-token default the same call takes 2.85 GB.
[ADR 01011](https://github.com/hawkeyexl/ts-inference/blob/main/adrs/01011-size-the-local-context-to-the-prompt.md)
records the measurements and the options weighed.

### Decisions

`LlamaCppProvider` is a [decision provider](/inference/reference/providers/#decisions). `decide()`
reads the model's own probability for each option, so `confidence` is a measurement, not generated
text.

Each question becomes one user turn under a fixed system prompt. The options are lettered A, B, C in
`criteria` order, each shown with its meaning (or its id, when the meaning is empty). The state comes
first, as given when it is a string and as indented JSON otherwise:

```text
# State

<state>

# Question

<instructions>

A. <meaning of the first option>
B. <meaning of the second option>

Reply with the letter of one option.
```

The model's chat template wraps the turn, and the assistant's turn opens with `Answer:`. The
provider reads the next-token probability of each letter, summed over the letter's token with and
without a leading space, and [normalizes](/inference/reference/providers/#decisions) them over the
options. It reads them among the 40 most likely next tokens, and a letter outside those weighs 0.
A question with no letter among them is read again over the whole vocabulary. Thinking is off: Qwen3 and Qwen3.5 get the empty think block their template uses for that,
and Gemma 4 gets its non-reasoning prompt. Nothing is generated, so `usage.outputTokens` is 0.

Every question of a request runs on one session, and the state is evaluated once. After each
question the session returns to the end of the state, which the runtime reports as `reuse`:

| `reuse` | How | Models |
|---|---|---|
| `"erase"` | the question's tokens are removed from the context | attention models, such as Granite 4.1 |
| `"checkpoint"` | the state is restored from a snapshot taken after it | hybrid and recurrent models, such as Qwen3.5 |
| `"reevaluate"` | the state is evaluated again | a model that can do neither |

The answers are the same either way; only the cost differs. `reuse` is on the runtime's result, not
on `DecideResponse`. Wrap `defaultLlamaRuntime()` to see it, as the live suite does.

The context is sized as for `completeJSON`, with the longest question's prompt as the user prompt
and 8 tokens for the answer. `stateLimit()` returns the tokens left for the state plus the longest
question: the training context, or `contextSize` when set, less the system prompt, the 512-token
template overhead, the answer, and 128 tokens for the provider's own headings and letters. A
request within it is never refused. A question has at most 26 options.

On an RTX 4090 with CUDA, a three-question decision on `qwen3.5-4b` takes about 160 ms a question
once the weights are loaded. On the CPU it takes about 11 s a question.
[ADR 01016](https://github.com/hawkeyexl/ts-inference/blob/main/adrs/01016-decide-on-local-models-from-letter-probabilities.md)
records the design.

### Shared-prefix completions

[`completeJSONShared`](/inference/reference/completion/#completejsonshared) runs every item on one
session, the way `decide()` runs every question. The system prompt is yours with the schema
restated, as for `completeJSON`. Each item's user turn is `shared + item`, rendered whole in the
model's chat template with thinking off, as for decisions. The tokens every item's turn shares are
evaluated once.

Each item then evaluates only its own tail and generates its answer under the schema's grammar. Generation
stops when the JSON value is complete, when the model ends its turn, or at the item's token limit.
The session then returns to the end of the shared tokens, and reports how as `reuse`, with the
values in the table above. Unlike a decision, `reuse` is on the response, `SharedJSONResponse.reuse`.

The context is sized by the same rule as `completeJSON`, with the longest item's turn as the user
prompt. It holds one item at a time, so 30 items need no more context than the longest one. With
`maxTokens` unset, each item may use the room its context has left. `thoughtTokens` does not apply,
because thinking is off.

An item whose answer is cut off, does not parse, or fails the schema is `{ error }`, and the next
item runs as usual. A failed answer is not retried here: at temperature 0 the same prefix
generates the same tokens. A worker crash retries the whole request on the next backend, as for a
prompt. Through the [model host](#the-model-host) the request is one job in the model's queue.

On an RTX 4090 with CUDA, 30 rules over a turn of about 3700 tokens, with a three-integer schema:

| Model | `reuse` | 30 items | Per item | One item alone |
|---|---|---|---|---|
| `qwen3.5-4b` | `checkpoint` | 7.0 s | about 230 ms | about 730 ms |
| `granite-4.1-3b-q2` | `erase` | 3.6 s | about 120 ms | about 800 ms |

The last column is what each item costs when the turn is evaluated for it alone, which is what 30
independent `completeJSON` calls pay.
[ADR 01018](https://github.com/hawkeyexl/ts-inference/blob/main/adrs/01018-structured-answers-over-a-shared-prefix.md)
records the design.

## The worker process and the backend

The real runtime does not run llama.cpp in your process. It forks a worker, `llama-worker.js` from
beside the package's `index.js`, and sends it each load, session and prompt over IPC. Your process
never initialises a GPU backend.

The reason is that llama.cpp reports a fatal GPU error by aborting the process (`GGML_ABORT`), and
no `try` can catch that. On some Windows machines with an NVIDIA GPU, node-llama-cpp's prebuilt CUDA
backend does this intermittently mid-generation, printing `ggml-cuda.cu:106: CUDA error`. In-process,
that ended the consumer and every result it had computed. In a worker, it ends the worker.

| `gpu` (or `NODE_LLAMA_CPP_GPU`) | Starts on | When a worker crashes |
|---|---|---|
| unset, or `"auto"` | the best backend this machine has | the call is retried on the next one — CUDA, then Vulkan, then the CPU — and the crashed backend is skipped for the rest of the process |
| `"cuda"`, `"vulkan"`, `"metal"`, or `false` (CPU) | that backend | never replaced: the call fails with an `InferenceError` naming the crash, recorded on `run.error` |

Each switch is announced once on stderr; the messages are in the
[warnings reference](/inference/reference/warnings/). The CPU is a last resort, because it is about
50× slower. If you would rather fail fast than wait, pin a backend.

Only an abnormal exit counts as a crash. An ordinary error, such as a context overflow, a grammar
error or a missing model file, passes through unchanged on the same worker and is never retried on
another backend.

The backend is not part of the provider identity or the cache key. Two backends run the same
weights under the same grammar, and a cache that missed after every fallback would make you pay
for the work twice.

One worker serves every model loaded for a backend. It holds your process open only while a call is
in flight, so a script that never calls `disposeLlamaModels()` still exits when its work is done, and
the worker exits with it. If you bundle this package into a single file, the worker cannot be found.
The runtime then runs in-process as before and warns that a native crash will end the process.

[ADR 01012](https://github.com/hawkeyexl/ts-inference/blob/main/adrs/01012-isolate-local-inference-in-a-worker-process.md)
records the crash, the options weighed, and why a pre-flight probe cannot replace this.

## The model host

A process that makes one call and exits pays a full model load on every run: seconds, and gigabytes
read again. Several such processes at once each load their own copy. Hooks are the usual case, since
each hook is a fresh process. The model host is one detached process, per user and runtime
directory, that keeps models loaded for every process that calls it.

```ts
type ModelHostMode = "off" | "connect" | "spawn";

function leaseModelHost(options: LeaseModelHostOptions): Promise<{ pid: number } | null>;
function modelHostStatus(): Promise<ModelHostStatus | null>;
function releaseModelHost(
  options: { session: string } | { all: true },
): Promise<ReleaseModelHostResult>;

class ModelHostBusyError extends InferenceError {}   // name: "ModelHostBusyError"

interface LeaseModelHostOptions {
  model: string;            // a concrete model, as the provider takes it
  session: string;          // names the lease
  keepAlive?: number;       // ms the lease outlives its last use; default 600000
  spawn?: boolean;          // start a host when none runs; default true
  modelsDirectory?: string;
  gpu?: LlamaGpu;
  hostWaitMs?: number;      // ms the load may wait in the queue; default: no limit
}

interface ModelHostStatus {
  pid: number;
  models: { model: string; sessions: number; idleMs: number; queued: number }[];
}

interface ReleaseModelHostResult {
  released: string[];       // sessions whose leases were dropped
  unloaded: string[];       // models unloaded as a result
  hostStopped: boolean;
}
```

Turn it on per provider with `llamaCpp.host`:

| `host` | Where calls run |
|---|---|
| `"off"` (default) | In your process's own worker, as described above. Nothing changes. |
| `"connect"` | In a running host. When none runs, or it dies mid-call, in your process's own worker instead. |
| `"spawn"` | In a host, which the first call starts when none runs. A host that dies mid-call is replaced and the call retried once. |

`host` is ignored when `runtime` is injected. The host runs the same provider, so the worker, the
backend fallback, context sizing and every error are unchanged; only the process holding the weights
moves. The host is `llama-hostd.js` beside the package's `index.js`, started detached, so it
outlives the process that started it.

Calls queue per model. One call per model runs at a time, in arrival order. Two models load side by
side only when [`fits`](#preparing-a-model) says the second fits beside the first; otherwise the
host unloads the idle one first, and a call that must wait for memory holds back the calls behind
it. A call still queued after `hostWaitMs` is withdrawn with `ModelHostBusyError`, and nothing
runs.

A model stays loaded while it is busy or queued, while a live lease holds it, and for `keepAlive`
after its last call finishes. The keepAlive is the latest call's, default 600000 ms (10 minutes); `0`
unloads it as soon as nothing holds it or waits for it. The host exits when nothing is loaded and no
client is connected, so it never lingers on its own.

A lease is a named hold on a model:

- `leaseModelHost({ model, session })` takes one and loads the model, so later calls find it warm.
  Call it when a session starts.
- A call whose provider has `session` set takes that lease, or renews it if it exists. A lease keeps
  the keepAlive it was taken with.
- A lease lapses once unused for its keepAlive.
- `releaseModelHost({ session })` drops that session's leases and unloads any model no other lease
  holds. With `{ all: true }`, it drops every lease, withdraws queued calls, waits for running ones,
  unloads everything and stops the host. Both resolve once the memory is free.

`modelHostStatus()` and `releaseModelHost()` never start a host; with none running they return
`null` and an empty result. In status, `sessions` counts live leases, `idleMs` is the time since
the model's last call (0 while one runs), and `queued` counts calls waiting behind it.

The host lives in `<runtime dir>/host/`, a directory only you can open where the OS allows it,
so `INFERENCE_RUNTIME_DIR` moves it too. It listens on a Unix socket there, or on Windows on the
named pipe `\.pipehawkeyexl-inference-<user>-<hash>`. A client must open with the token the
host writes to `host.token` in that directory, readable only by you; any other first message
closes the connection. A start lock lets one host start when several clients start one at once, and
a lock or socket left by a host that died is reclaimed. The host's stderr, including the backend
switch warnings, goes to `host.log` there, not to your console.

[ADR 01017](https://github.com/hawkeyexl/ts-inference/blob/main/adrs/01017-keep-local-models-loaded-in-a-model-host.md)
records the design and the options weighed.

## Getting the runtime

`node-llama-cpp` is an **optional peer dependency**, and npm does not install optional peers. Since
detection ends at `llama-cpp` precisely because it needs no key and no account, a machine with no
credentials and no binding would otherwise have nothing left to fall back to.

So the library installs it on demand, into a directory it owns — never your `node_modules`, your
`package.json`, or your lockfile.

```ts
function defaultLlamaRuntimeDirectory(env?: Record<string, string | undefined>): string;
function nodeLlamaCppStatus(options?: RuntimeInstallOptions): Promise<RuntimeStatus>;
function importNodeLlamaCpp(options?: RuntimeInstallOptions): Promise<unknown>;
function resetRuntimeInstall(): void;

type RuntimeStatus =
  | { state: "present" }
  | { state: "installable"; directory: string }
  | { state: "refused"; reason: string };

interface RuntimeInstallOptions {
  directory?: string;   // defaults to defaultLlamaRuntimeDirectory()
  exec?: ExecFn;        // test seam
  env?: Record<string, string | undefined>;
  timeoutMs?: number;   // default 15 minutes
  importShim?: (url: string) => Promise<unknown>;   // test seam
  probeImport?: () => Promise<unknown>;             // test seam
}
```

Resolution runs in three steps, stopping at the first that works: your own installed copy, then
`<runtime dir>/loader.mjs` from an earlier run, then an install.

| Variable | Effect |
|---|---|
| `INFERENCE_RUNTIME_DIR` | Where the binding is installed. Default `~/.hawkeyexl-inference/runtime`. |
| `INFERENCE_NO_AUTO_INSTALL` | Set to anything non-empty to refuse installing. `llama-cpp` then reports unavailable instead. |

`nodeLlamaCppStatus` answers whether the runtime is usable **without installing it**. That is what
keeps `availableProviders()` a query: asking a machine what it can do never changes what it can do.
The install happens later, when the provider is actually resolved, and warns once before it starts.

`importNodeLlamaCpp` is exported so you can pre-fetch deliberately — in a Docker build, say, so the
first real run does not pay for it.

<Aside type="caution" title="It is a native module">
  Prebuilt binaries cover win32-x64, darwin-arm64 and linux-x64. Anywhere else falls back to a CMake
  build that needs a toolchain and can take minutes, which is why the install timeout is 15 minutes
  rather than the usual 60 seconds. Set `INFERENCE_NO_AUTO_INSTALL` if you would rather it never
  tried.
</Aside>

The shim is written **only after npm exits 0**, so an interrupted install leaves a prefix that is
retried rather than one that looks ready and is not. Concurrent callers in one process share a
single install; concurrent processes serialise on a lock file in the prefix.
